# 异步协作与任务运行时

## 这个操作解决什么问题

一个真正可工作的 Agent 不能只处理同步问答。它还需要：

- 任务面板记录长期目标
- 后台任务持续运行命令
- 子代理并行执行子任务
- 定时调度把未来 prompt 注入主循环
- 团队协议让不同执行单元交换消息
- worktree 车道隔离并行修改

这些能力如果直接塞进主循环，会让主循环变成任务调度器。

## 为什么这么做

异步能力的共同点是：它们不一定在当前模型请求内完成，但结果需要回到下一轮 Agent 上下文中。

所以本项目把它们分成两部分：

- 各自工具内部负责创建、持久化、执行和状态流转。
- QueryPreparation / QueryNotifications 在下一轮开始前 drain 通知，并注入动态 system messages。

也就是说，异步系统不是直接打断主循环，而是通过通知队列回流到下一轮。

## 怎么做

1. TaskBoard 管任务状态和 active task。
2. BackgroundTask 管后台命令和完成通知。
3. Subagent 管子代理生命周期和结果通知。
4. Scheduler 管未来 prompt 命中和 durable notification。
5. Team 管消息和请求协议。
6. QueryNotifications 把这些通知格式化成模型可读上下文。
7. QueryPreparation 在模型请求前收集这些动态上下文。

## 优点

- 主循环保持同步、可预测。
- 异步结果不会丢，下一轮可以被模型看到。
- 子代理、后台任务、调度器可以独立演进。
- 任务状态和通知回流有明确位置。

## 代价和风险

- 通知文案会影响模型行为，必须谨慎维护。
- durable notification 需要处理重复触发和 drain 时机。
- 异步能力越多，用户越需要可视化或状态查询来理解系统当前在做什么。

## 怎么用它讲这个项目

可以这样讲：

> 这个 Agent 不只是一轮模型调用，而是一个带异步回流的运行时。后台任务、子代理、调度器和团队消息都先进入各自状态系统，再通过 notification 在下一轮注入模型上下文。

这能解释为什么项目里既有 tools，又有 notification service 和 query preparation。
