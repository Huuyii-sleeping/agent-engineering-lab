# 规格驱动与收口工作法

## 这个操作解决什么问题

长期重构最怕两个问题：

- 只改代码，不知道为什么改。
- 文档按每次执行流水账堆积，最后没人愿意读。

前一阶段已经暴露出这个问题：每轮 PRD 都写学习沉淀，结果很多文档讲的是同一种“边界收口”，对理解项目帮助有限。

## 为什么这么做

OpenSpec 和 PRD 适合记录“这次变更的范围和验收”，但学习文档应该服务于“长期理解项目”。

所以后续分工应调整为：

- PRD：描述本次要改什么。
- OpenSpec：约束能力和验收。
- commit：保存实现结果。
- operations 文档：沉淀可复用的操作类型和架构思路。
- 历史学习文档：只作为追溯材料，不作为主阅读路径。

## 怎么做

1. 如果是一次具体实现，仍然写 PRD / OpenSpec。
2. 如果只是同类边界收口，不再每次新写一篇重复学习文档。
3. 学习沉淀优先更新 `operations/` 下的统一类型文档。
4. 每篇文档固定回答：
   - 为什么做
   - 怎么做
   - 优点
   - 代价
   - 如何讲这个项目
5. 交接文档只记录当前状态，不替代长期知识库。

## 优点

- 文档数量减少，阅读路径更清晰。
- 文档更适合讲项目，而不是复盘某次改动。
- 后续维护者能从操作类型理解架构决策。
- PRD 和学习文档职责分开，减少重复。

## 代价和风险

- 单篇文档会更抽象，需要定期用真实代码校准。
- 历史 PRD 细节不在主文档里，需要通过 archive 查。
- 如果 operations 文档长期不更新，也会变成新的过时入口。

## 怎么用它讲这个项目

可以这样讲：

> 这个项目的沉淀分两层：OpenSpec/PRD 记录每次变更的边界，operations 文档记录可复用的工程方法。我们不希望文档只是改动流水账，而是能讲清楚为什么这个 Agent runtime 要这样设计。

这也是后续文档维护的核心原则。
