# 架构总览与外部对照

这篇文档用来回答两个问题：

1. 当前仓库的主架构到底分成哪几层。
2. 对照外部参考文章 [liuup/claude-code-analysis/analysis/01-architecture-overview.md](https://github.com/liuup/claude-code-analysis/blob/main/analysis/01-architecture-overview.md)，我们哪些已经做到，哪些做得更强，哪些暂时没有做。

## 先给结论

- 如果只看那篇文章的主干分层：我们已经覆盖了大部分核心层，尤其是轻量入口、组合根、Query runtime、工具总线、Memory/MCP。
- 如果看完整平台形态：我们并没有实现独立的 `remote-control / bridge / daemon` 远程平台层，所以不能说“全文提到的所有东西都一模一样做到了”。
- 如果看工程化深度：我们在权限审批、交付验证、技能加载、规范驱动、交接闭环这些方面，已经明显比那篇文章里的总览更完整。

## 一句话架构总结

这个仓库的核心不是“把 Agent 写在 CLI 里”，而是：

> 用统一组合根装配一个可复用的 Agent runtime，再让 CLI、TUI、headless、HTTP service 和 MCP server 这些入口只负责各自的输入输出适配。

## 先看主链路

如果只想快速理解系统怎么跑，一条主链路就够了：

1. 入口层解析模式和输入：
   - `main.ts`
   - `entrypoints/cli-dispatcher.ts`
2. 组合根装配 runtime：
   - `bootstrap/app-runtime.ts`
   - `services/runtime-services.ts`
3. Query runtime 执行一轮 Agent：
   - `runtime/query-engine.ts`
   - `runtime/query-preparation.ts`
   - `runtime/query-model.ts`
   - `runtime/query-tools.ts`
   - `runtime/query-finalization.ts`
4. Tool / Memory / Notification / Delivery 在各自边界内完成副作用和状态流转。
5. 结果回到当前表面，或者作为异步通知在下一轮再注入模型上下文。

## 对照外部文章：哪些已经做到

下面按那篇文章里常见的架构块来对照。

### 已覆盖

- 轻量 `main` + 分流 dispatcher
- 多入口形态：CLI / headless / TUI / server / MCP
- 独立的初始化与组合根
- Query runtime 作为共享内核
- Tool bus 支持 native / subagent / MCP
- Memory 注入与持久化
- MCP client / registry / public facade 分层

### 已覆盖且做得更强

- 权限和审批是产品化 surface，不只是内部 helper
- 交付验证已经进入 runtime finalization，而不是靠人工补做
- skills、prompt dump、architecture dump 都是本地 inspection surface
- transcript browser、palette、workflow 切换让本地控制面更完整
- OpenSpec、PRD、交接文档把“实现完成”扩展成“可交接、可验证、可归档”

### 没有直接对齐的部分

- 没有独立 `remote-control` 平台层
- 没有单独 daemon / bridge 进程模型
- 没有远程 websocket reconnect 或多端桥接协议
- 没有把工具并发暴露为单独的 public batch scheduling API

这些不是“遗漏后忘了补”，而是当前产品边界没有往远程代理平台那一层扩。

## 为什么我认为现在比那篇总览更强

不是因为层数更多，而是因为已经把“能讲清楚的架构”做成“能直接操作的产品面”：

- 外部文章讲到入口和运行时分层，我们已经做成 `agent-cli architecture` 和 `/architecture`。
- 外部文章讲到工具与 MCP，我们已经把审批、MCP、subagent、background、scheduler 接成统一控制面。
- 外部文章更偏架构总览，我们已经把交付验证、prompt inspection、skills 和 handoff 全部接进日常工作流。

换句话说：

> 那篇文章更像“怎么理解 Claude Code 的架构”。
> 这个仓库现在更接近“把这些分层真的做成一个可工作的工程化 Agent”。

## 之后如果还要继续补强，优先级是什么

如果要继续往“比外部总览更完整的平台架构”推进，优先级建议是：

1. 增加显式 remote runtime / bridge 设计，而不是只保留本地交互面。
2. 给异步能力补更强的统一可视化状态面，而不是分散在多个命令里。
3. 评估是否需要引入真正的多执行单元远程调度层，而不只是本地 subagent / background runtime。
