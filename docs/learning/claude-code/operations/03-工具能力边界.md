# 工具能力边界

## 这个操作解决什么问题

Agent 工具系统最容易混在一起：

- 工具有哪些
- schema 怎么暴露给模型
- 工具怎么预览
- 权限怎么检查
- native / subagent / MCP 怎么分发
- 工具结果怎么回填给模型
- 工具副作用怎么被记录

如果这些都在一个工具文件里，新增工具来源或调整权限策略会非常危险。

## 为什么这么做

工具系统有两个不同层次：

- 工具目录层：负责告诉模型“有哪些工具、schema 是什么、metadata 是什么”。
- 工具执行层：负责真正执行工具，并处理 builtin、subagent、MCP 等不同 target。

再往下，每类复杂工具还应该有自己的内部边界：

- Security：policy、approval、manager、facade。
- Team：store、protocol、manager、facade。
- Worktree：store、runner、manager、facade。
- Scheduler：cron、store、manager、facade。
- BackgroundTask / Subagent：executor / runner、manager、facade。

## 怎么做

1. ToolService 只组合 catalog 和 executor。
2. ToolExecutor 只做 target dispatch。
3. Native、subagent、MCP 的执行策略分别收口。
4. 工具 facade 只暴露 tool schema 和 public handler。
5. 工具内部复杂状态下沉到 store / manager / protocol / runner。
6. QueryToolStage 只处理“模型请求工具调用后，如何执行并回填结果”。

## 优点

- 新增工具来源时，不需要改主循环。
- 调整某类工具内部逻辑时，不影响其他工具。
- 工具 schema、执行、权限、观测的职责更清楚。
- MCP 等外部能力能接入统一工具视图。

## 代价和风险

- 初看目录会多，尤其 tools 下有很多 `*-manager`、`*-store`、`*-types`。
- 小工具如果过早拆分，会显得重。
- facade 和 manager 的边界要持续保持，否则 facade 会再次膨胀。

## 怎么用它讲这个项目

可以这样讲：

> 工具系统不是一堆函数注册表，而是一套工具能力总线。模型只看到统一 schema，QueryToolStage 只看到统一执行契约，底层 native、subagent、MCP、security、team、worktree 都各自维护自己的内部边界。

这能解释为什么工具目录比普通 demo 项目复杂，因为它服务的是多来源、可治理、可观测的工具执行。
