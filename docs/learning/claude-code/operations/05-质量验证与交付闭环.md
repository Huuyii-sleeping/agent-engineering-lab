# 质量验证与交付闭环

## 这个操作解决什么问题

Agent 会修改代码，但修改代码不等于完成任务。一个工程化 Agent 必须知道：

- 哪些文件被改了
- 是否有写副作用
- 是否需要自动验证
- 验证失败怎么摘要给模型
- 验证报告怎么保存
- 用户换电脑或接手时怎么看当前状态

没有交付闭环，Agent 很容易停在“我改了”而不是“我验证过”。

## 为什么这么做

本项目把 delivery 当成运行时的一部分，而不是外部人工步骤。

核心逻辑是：

- 工具执行阶段标记写副作用和 touched paths。
- finalization 阶段根据配置自动运行 delivery validation。
- delivery report 保存验证结果。
- 验证摘要回填到会话历史，让模型知道当前状态。
- OpenSpec 和交接文档记录最终状态。

## 怎么做

1. 写类工具成功后记录 touched paths。
2. QueryFinalization 判断是否触发 auto delivery。
3. Delivery plan / runner / report store 分别负责计划、执行、报告。
4. 验证摘要作为 assistant message 回填。
5. 收口完成后跑 focused tests、build、OpenSpec strict、diff check。
6. 本地 commit，但不自动 push。

## 优点

- 修改和验证绑定在同一条主链路里。
- 失败信息能回到模型上下文，便于下一轮修复。
- 交接时能知道哪些验证跑过。
- OpenSpec active changes 为空时，项目状态更清楚。

## 代价和风险

- 自动验证会增加运行时间。
- 验证摘要如果写得太粗，会对后续模型帮助有限。
- 如果验证命令覆盖不足，仍可能产生“看似通过”的风险。

## 怎么用它讲这个项目

可以这样讲：

> 这个项目把交付验证做进 Agent 生命周期里。工具执行产生写副作用后，收尾阶段会自动验证并把结果回灌给模型，所以 Agent 不只是能改代码，还能形成修改、验证、记录、交接的闭环。

这能解释为什么有 delivery 模块、auto delivery finalizer、OpenSpec archive 和对话交接文档。
