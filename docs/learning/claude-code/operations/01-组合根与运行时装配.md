# 组合根与运行时装配

## 这个操作解决什么问题

Agent 项目很容易从入口文件开始失控：CLI、HTTP 服务、未来 Web 入口各自创建模型客户端、工具、记忆、hook、观测、任务服务。短期能跑，长期会出现两个问题：

- 同一个能力在不同入口重复装配，行为不一致。
- 新增能力时需要到处改入口，入口越来越像业务大杂烩。

组合根的作用是把“对象怎么创建、依赖怎么连起来”集中起来，让入口只负责输入输出适配。

## 为什么这么做

这个项目有多个交互表面：

- CLI 输入一轮用户请求。
- HTTP service 管理多 session。
- 后续可能有 Web console 或后台任务入口。

这些入口不应该各自实现一套 Agent。它们应该共享同一套 runtime，只在“请求从哪里来、结果怎么返回”上不同。

所以核心思路是：

- `bootstrap/app-runtime.ts` 负责装配应用依赖。
- `RuntimeServices` 负责把横切 service 收成依赖包。
- CLI / HTTP service 只拿装配好的 query engine 和 services 使用。

## 怎么做

1. 把模型客户端、工具服务、delivery、hook、memory、notification、observability、runtime coordination 收到统一装配入口。
2. QueryEngine 不直接 new 这些 service，只接收依赖包。
3. 测试里允许按单项 service override，而不是每个测试手写完整世界。
4. 入口文件只做参数解析、session 管理和结果输出。

## 优点

- 新入口接入成本低，只需要复用 app runtime。
- 测试更稳定，可以替换某个 service 而不影响其他依赖。
- 依赖关系更可见，项目结构更容易讲清楚。
- 入口不再吞掉核心业务逻辑。

## 代价和风险

- 初期会多一些类型和装配文件，看起来比直接 new 对象更复杂。
- 如果依赖包无节制扩大，也会变成“万能上下文对象”。
- 组合根只解决装配，不解决模块内部职责混乱；内部仍需要独立边界。

## 怎么用它讲这个项目

可以这样讲：

> 这个项目不是把 Agent 写在 CLI 里，而是把 Agent runtime 做成可复用内核。CLI、HTTP service 都只是外层适配器，真正的模型请求、工具执行、记忆、hook、交付验证都由统一 app runtime 装配。

这句话能解释为什么仓库里有 `bootstrap/`、`services/` 和 `runtime/` 三层。
