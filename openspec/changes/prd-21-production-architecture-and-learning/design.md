## Context

当前仓库存在三份重要基线：

- `typescript/`：按章节演进的教学源码，能看清能力是如何逐步长出来的。
- `apps/agent-cli/`：当前可运行、已融合多轮 PRD 的实现。
- Claude Code 参考源码与分析材料：提供了更接近真实产品的分层基调，尤其体现在 `src/main.tsx`、`src/QueryEngine.ts`、`src/query.ts`、`src/Tool.ts` 及 `src/` 目录结构中。

当前问题不是“能力不够”，而是“能力已经不少，但结构还不够稳”。如果继续沿用现在的方式往 `agent-loop.ts`、入口文件和工具路由上叠加职责，后续做 Web 展示、更多入口、更多工具、更多模式时，维护成本会明显上升。

本次变更的本质，是先把后续数轮重构的基调定清楚，并把学习沉淀纳入正式交付物。

## Goals / Non-Goals

**Goals:**

- 明确本仓库的生产级目标分层，而不是继续让结构隐含在代码里。
- 为 CLI、HTTP service、未来 Web 接入建立共享应用装配方向。
- 把 Query runtime、tool runtime、service/state/hook 等层的边界梳理为可逐步演进的路线。
- 把外部源码阅读和本地映射沉淀为仓库资产。

**Non-Goals:**

- 不在本 change 内直接完成全部架构重写。
- 不要求目录结构和 Claude Code 参考源码一一对应。
- 不引入仅为“像上游”而存在的复杂度。

## Decisions

### 决策 1：采用“以参考源码为基调，但不做逐文件镜像复制”的重构策略

本次以 Claude Code `src/` 的分层思想为主参考，但不把“文件名、目录数、UI 结构”当成硬性复制目标。

选择原因：

- 我们要吸收的是生产级结构经验，而不是做外形克隆。
- 当前仓库已有自己的能力沉淀和演进历史，必须尊重现有实现和测试资产。

备选方案：

- 直接按上游目录结构大规模平移
  - 不采用原因：风险高、上下文大、对当前仓库不够尊重，且难以验证每一步收益。

### 决策 2：先建立 bootstrap / composition root，再逐步拆 runtime

后续重构顺序优先从共享装配入手，而不是一开始就拆所有核心逻辑。

选择原因：

- 入口层共享装配是 CLI、HTTP service、未来 Web 接入复用的前提。
- 如果没有 composition root，后续 runtime 拆分很容易再次分散。

备选方案：

- 先拆 `agent-loop.ts`
  - 不采用原因：会先动到最复杂的核心模块，但入口装配问题仍然存在，容易反复返工。

### 决策 3：Query runtime 和 Tool runtime 作为两条独立边界推进

后续重构把“会话 / query 生命周期”和“工具定义 / 路由 / 权限 / 执行上下文”视为两条独立主线。

选择原因：

- 参考源码里 `QueryEngine` 与 `Tool` 契约都不是附属概念，而是稳定边界。
- 当前仓库里这两部分已经有雏形，适合继续显式化，而不是重新发明。

备选方案：

- 继续按能力点把逻辑分别塞回 `agent-loop.ts` 和 `tools/index.ts`
  - 不采用原因：只会继续增加局部复杂度，不能提升整体可维护性。

### 决策 4：学习沉淀文档作为正式交付，不作为额外备注

凡是作为本轮架构参考的外部材料和本地源码映射，都必须以仓库文档形式落地。

选择原因：

- 用户明确把这些材料视为学习资产。
- 没有文档沉淀，后续阶段会重复读、重复解释、重复决策。

备选方案：

- 仅在会话中说明
  - 不采用原因：不可复用、不可审阅、无法形成长期知识库。

## Risks / Trade-offs

- [Risk] 范围过大，导致后续实现阶段失去边界
  - Mitigation：本 change 只定架构主线、阶段边界和学习沉淀要求；实际实现继续拆成小步。

- [Risk] 参考源码过于复杂，导致本仓库引入不必要复杂度
  - Mitigation：仅采纳“对当前仓库有明确收益”的分层和职责边界，不追求形式一致。

- [Risk] 学习文档变成只写不看的附属材料
  - Mitigation：要求每轮架构 change 都回写“采纳/不采纳/原因”，让文档直接服务实现决策。

## Migration Plan

1. 先完成 `PRD-21`、OpenSpec artifacts 与第一份学习沉淀文档。
2. 下一轮实现 change 优先建立共享 bootstrap / composition root。
3. 再逐步抽离 query runtime 与 tool runtime 边界。
4. 完成核心分层后，再推进 Web 展示与更完整的产品化交互。

回滚策略：

- 本 change 主要是规划与文档资产，回滚风险很低。
- 后续实现阶段若发现某条架构路线不合适，应通过学习文档与 design 记录修正理由，而不是继续隐式偏移。
